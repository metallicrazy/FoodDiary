# FoodDiary — handover notes for anyone continuing development

This file is for a developer or AI assistant picking up the project. `README.md` is the user-facing guide; this document records **how the app is built, the product decisions behind it, and the release routine**, so edits can continue without re-deriving anything.

**Current version: see line 3 of `README.md`, `VERSION` in `sw.js`, and `APP_VERSION` in `js/app.js` — all three must match.**

---

## 1. What this is

A single-user **Progressive Web App** (plain HTML/CSS/JS, no build step, no framework) hosted on **GitHub Pages** and installed to the iPhone/Android home screen. Chosen specifically to avoid an Apple developer account or any hosting cost. The owner is a UK user; units are metric (kg, cm, g/ml, kcal), language en-GB.

Everything the user enters stays on the device (localStorage for the diary document, IndexedDB for photos and safety copies). There is no backend, no login, no analytics.

## 2. File map

| File | Role |
|---|---|
| `index.html` | App shell — four screens (`#view-today`, `#view-add`, `#view-progress`, `#view-me`), bottom tab bar, a single reusable bottom sheet (`#sheet`) and toast. |
| `css/styles.css` | Design system. CSS variables at the top; dark mode via `prefers-color-scheme`. Accent green; macro colours protein indigo / carbs amber / fat pink. |
| `js/portions.js` | Built-in UK portion table (~80 name patterns → unit + grams, e.g. egg 58 g, slice 36 g, rasher 25 g) for CoFID foods, which carry no serving data. `Portions.forName(name)`; has an EXCLUDE list so dishes/juices/dried forms don't get unit portions. |
| `js/names.js` | Plain-English titles for CoFID names: `Names.friendly(cofidName)`. ~120 hand-written OVERRIDES for common foods plus rewrite rules (flesh only → peeled / boneless / meat only by food type; 'old' potatoes → dropped; 'boiled in unsalted water' → boiled; cooking word moved to the front; qualifiers in brackets). | `js/ranking.js` | Human-feeling ranking for CoFID search: `Ranking.scoreName(query, name, {recent})`. Word-start bonuses, head-of-name match, demotes composite dishes (DISH) and exotic variants (EXOTIC), promotes as-eaten forms, plus a CURATED map of ~100 everyday words → ordered regexes pinned to the top (egg → chicken eggs boiled/raw/fried…). Recents get +8. Since 1.21.0 `Ranking.prepare(query)` does the query work once and remembers per-name facts, so a scan of all UK foods takes ~0.5 ms instead of ~6 ms; `scoreName` still exists (same scores) for tests. |
| `js/scanner.js` | Camera barcode scanner (1.18.0, replaced html5-qrcode which was slow on iPhone). Owner declined torch / scan-frame / beep extras. |

| `js/nutrition.js` | **Pure functions, no DOM** (also loadable in Node): BMR/targets, macro presets & rebalancing, BMI & healthy range, portion scaling, Open Food Facts → food mapping, CoFID sheet parsing, nutrition-label OCR text parsing, date helpers. | `js/app.js` | All UI logic: rendering each screen, the food sheet, scanner, OCR flow, recipe builder + diary picker, charts, Me screen, auto-update. ~1,000 lines, organised by `/* ===== SECTION ===== */` banners. |
| `sw.js` | Service worker: offline shell, long-lived caches for the UK food list / libraries / product pictures, update behaviour. **Bump `VERSION` on every release**; bump `DATA` only when `data/cofid.json` changes and `LIBS` only when a CDN library version changes (§6). |

## 3. Data model (Store.state)

```
profile:  { sex, age, heightCm, weightKg (current = latest reading), activity, goal,
            targetBmi (default 24.9), startWeightKg, startDate }
targets:  { kcal, protein, carbs, fat, auto (bool), preset ('lowcarb'|'balanced'|'keto'|'custom'), ketoCarbs }
diary:    { 'YYYY-MM-DD': [ { id, time, food (slim snapshot), grams, kcal, protein, carbs, fat } ] }
weights:  [ { date: 'YYYY-MM-DD', kg } ]   // one per day, sorted
customFoods, recipes, favourites, recents (max 30), cache (barcode → food, 30-day TTL)
burnDismissed: { kcal, date } | null   // 'Not now' on a real-burn suggestion (1.22.0)
recipeCategories: [{ id: 'cat:…', name }] (A–Z); recipe.categoryId (optional, one per recipe); recipeFilter: null | category id | 'none'   // 1.25.0
  — normalise() drops a categoryId/recipeFilter that points at a missing category.
lastBackupAt: ISO | null; backupSnoozeUntil: dateKey | null   // 1.23.0 (checkinDone existed in 1.23.0 only; removed on load)
favourites: still stored and backed up, but no longer shown anywhere (feature removed from the UI in 1.23.0)
Quick-add diary entry (1.23.0): { quick: true, food: { id: 'quick', source: 'quick', name, kcal, protein, carbs, fat }, grams: 100, kcal, protein, carbs, fat }
  — food per-100 values = the totals at 100 g, so anything that scales by grams stays consistent.
IndexedDB safety keys: safety:before-1.20, safety:before-restore, safety:weekly, safety:weekly-prev (1.23.0)
```
Food objects are per-100 g/ml: `{ id, source ('off'|'cofid'|'custom'|'recipe'), name, brand, barcode, quantity, servingG, image, kcal, protein, carbs, fat, sugars, satFat, fibre, salt }`. Diary entries store a *snapshot* of the food so later edits to a custom food don't rewrite history.
`dataVersion`: 2 = photos stored once (1.20.0); data from before has none (treated as 1) and is upgraded on first launch.
`image` is one of: an Open Food Facts web URL; `'photo:<id>'` (user photo in IndexedDB); or — only transiently, before the next save, or in data not yet upgraded — an embedded `data:image/jpeg;base64,…` (256 px, typically 8–15 KB). **Never store embedded photos in the document** — every food snapshot (diary entries, recents, favourites, picks, recipe ingredients, drafts) carries `image`, so embedding them multiplied each photo hundreds of times and would have hit the ~5 MB localStorage limit within months (the owner's real data: 6 photos saved 26 times = 83 % of the document after 10 days).
Photos are never deleted when a food/recipe is removed (old diary entries may still show them); "Erase everything" removes all photos and safety copies.

## 4. Product decisions (agreed with the owner — don't undo without asking)

**Today → Journey card** (`renderJourney`, 1.11.0): sits above the calorie ring. Bar runs start weight → target-BMI weight, dot = current weight, % = share of distance covered (clamped 0–100; shows 0% and a red "x kg up since start" if weight rose). Deliberately minimal (owner trimmed it twice, 1.11.1–1.11.2): one row `start kg ━━●──── target kg (xx%)`, then (since 1.17.0) the **same sentence as the Progress BMI card** — "Lose x kg to reach target BMI of 24.9 (80.7 kg)." from the shared `bmiTargetMessage()` (replaced the old "Current BMI → Target BMI" line; hidden once the target is reached) — and the pace line from `averageIntake`/`daysToTarget`: "At your real intake you're on track for <date> — averaging n kcal above/below target" (or "not reaching target at this pace"). Target reached → celebratory state. Missing height/start weight → prompt to Me. Tapping goes to Progress. Handles gain goals (target above start).

**Diary**
- One flat time-stamped list per day (no Breakfast/Lunch/Dinner sections). Swipe left/right or use arrows to change day; tap the date to pick one.
- **Amounts are Qty × Size** (1.12.0). The food sheet has a Qty stepper and a Size field; total = qty × size, scaled from per-100 g values. If the food has a known unit (`portionFor()`: custom `unitG/unitName`, CoFID via `Portions`, recipe portion, or an OFF serving — label text decides can/bottle/bar/slice/pot/pack/piece/serving) it opens in **unit mode** ("By eggs": chips 1–4 eggs, size = g per egg) with a "By grams/ml" toggle; otherwise grams mode (chips 50/100/200, whole pack). Liquids (detected from quantity/name) show ml. Entries store `qty, sizeG, unit, unitPlural, liquid` alongside `grams`; `amountLabel()` renders "3 eggs · 174 g", "2 cans · 660 ml", "2 × 150 g · 300 g" or plain "150 g".
- **Wrong-day guard** (`logWithDayGuard`, 1.12.0): adding food (or Copy yesterday) while viewing any day other than today opens a sheet — **Log for today** (green, default) / **Log for <viewed day>** / **Cancel**. Viewing today → no prompt. The old "Add to" date dropdown on the food sheet was removed.

**Targets**
- Calories come from Mifflin–St Jeor × activity factor + goal delta (`Nutrition.calcTargets`), minimum 1,200, rounded to 10. Governed by the **"Calories from profile"** toggle (`targets.auto`).
  - ON: calories recalculate whenever profile changes **or a new weight is logged** (so maintenance drifts down as weight drops).
  - OFF: calories and macros are frozen at the typed values; logging weight does not touch them. **Activity and Goal are hidden** in the Profile card when OFF because they would have no effect.
- Macros come from a **diet preset** applied to the calorie figure: **Low carb (default)** 35/20/45, Balanced 30/40/30, **Keto** = carbs fixed in grams (slider 10–50 g, default 25), protein 25 % of kcal, fat fills the remainder.
- **Changing calories rescales macros to keep the same calorie split.** Editing one macro by hand keeps that value and scales the other two to fit the calories (`Nutrition.rebalance`), and the preset becomes `custom`; a custom split is remembered and reused when calories change later.
- Every change saves immediately: toast + a "Saved ✓" badge (`showSaved()`). There is deliberately no Save button.

**1.23.0 decisions (owner, 12 Oct 2026)**
- **Backups – reminder, not automatic upload.** Owner asked for automatic weekly backups. Explained: a web app can't save a file to the phone/OneDrive without a tap (iOS needs a user gesture for share/download; no background tasks on iOS), and OneDrive/Microsoft sign-in in a browser-only app gives refresh tokens that expire after 24 h, so it would need a sign-in each week on iPhone. Dropbox (PKCE + `token_access_type=offline`, non-expiring refresh token, CORS-enabled API) was offered as the only free fully-automatic option; **owner chose "reminder only"**. Built: (a) `lastBackupAt` recorded when the share sheet completes or the file downloads (a cancelled share does NOT count); (b) Today banner (since 1.24.0 placed between the calorie summary card and the Food log, in `#todayNotes`) "💾 No backup recorded on this phone yet / Last backup N days ago" when ≥ 7 days (or never, once ≥ 3 days are logged) with **Back up** and ✕ (snooze 3 days); (c) Me → Backup shows the last backup date; (d) `Store.weeklyCopy()` — automatic copy of the saved document into IndexedDB on the first launch ≥ 7 days after the last (current + previous kept), downloadable from Me → Backup. It reads what is already saved (no extra write at start-up — an extra write there bypassed the protected 1.20 upgrade path in testing). It protects against app problems, not a lost phone. If Dropbox is wanted later, see this note.
- **Favourites removed from the UI** (tab, ★ button, list above Recent). Owner: "not useful". Data kept (no deletion) so it could be brought back.
- **Quick add** — Add page button (action row is now a 2 × 2 grid on phones). Calories required (1–10,000), protein/carbs/fat and name optional; warns (doesn't block) if macros add up to > 125 % of the calories. Uses the wrong-day guard. Shown as "⚡ … Quick add" on Today; tap to edit/delete. Not added to Recents; excluded from the recipe "From my diary" picker; Copy yesterday keeps it a quick add. Counts in totals, Progress and real burn.
- **Spelling-tolerant search** — only when a search finds nothing: each word that appears in no UK food name is replaced by the closest real word (1 typo for 4–6 letters, 2 for 7+; swaps count as one; a half-typed word is compared with the start of longer words; candidates limited to words sharing the first or second letter). Note shown: "No exact match for “brocoli” – showing results for “broccoli”". Products (Open Food Facts) are searched with what was typed (brand names aren't in the UK word list) and only retried with the corrected words if that finds nothing. Known quirk: "muller" → "mullet" in the UK list (products still show Müller). Cost ~1–6 ms per keystroke (reusable typed-array rows, per-word cache, word list built once on first use).
- ~~Monday check-in~~ — built in 1.23.0, **removed in 1.24.0 at the owner's request ("I hate the Monday summary") — do not bring back.** `checkinDone` is dropped from saved data on load.

**Add page buttons (1.26.0, owner)**: one row of four, never two lines and never scrolling — "+ Custom", "+ Recipe", "⚡ Add" (Quick add), "⇩ Import" (full names kept in aria-label/title for screen readers). CSS grid `repeat(4, minmax(0, 1fr))`, gap 6 px, font `clamp(12px, 3.6vw, 14px)`, and on phones ≤ 340 px wide 11.5 px text / 4 px gaps / 2 px padding so it fits a 320 px-wide phone (≈ 69 px per button); with very large accessibility text the label is cut with "…" rather than wrapping. Keep any new action off this row (or replace one) — it has no room for a fifth.

**Recipe categories (1.25.0, owner's spec, 12 Oct 2026)**
- **One category per recipe** (owner's choice). Editor: "Category" native `<select>` (No category + A–Z list) with **＋** (inline box: type name → Add/Enter; an existing name in any case just selects it) and **✎** (shown once categories exist; inline list: rename by editing the name — applied on blur/Enter, never per keystroke; duplicates/blank refused and put back; 🗑 → inline "Delete “X”? **BMI rounding fix (1.24.0)** — owner reported 84.6 kg showing "Obese" while the scale said overweight below 84.7 kg. Cause: `Nutrition.bmi()` rounded to 1 dp *before* the category was chosen (168 cm: 84.6 kg = 29.97 → 30.0 → Obese). Now: `bmi()` **cuts off** to 1 dp (29.97 → 29.9), so the number shown always agrees with the category; tiny floating-point errors are removed first (64 kg at 160 cm is exactly 25.0 → Overweight). The scale's kg labels use `kgForBmi(line, h)` = the first 0.1 kg weight inside that band (rounded **up**: 168 cm → healthy from 52.3, overweight from 70.6, obese from 84.7). `healthyWeightRange()` max is the heaviest 0.1 kg that's still healthy (< 25) — 70.5 kg at 168 cm. The target line ("Lose X kg to reach target BMI of 24.9 (70.3 kg)") is unchanged. `tests/v124.mjs` checks every height 140–210 cm × weight 40–160 kg (85,271 combinations) plus the owner's backup.

**Layout (1.24.0, owner)**: Progress order = Weight → BMI → Real daily burn → Calories this week → Macros this week. Today = journey card → calorie summary → backup reminder (when due) → Food log.

**Real daily burn (1.22.0)** — owner's spec, agreed 12 Oct 2026. Card "Real daily burn" on Progress, under the Weight card (and, since 1.24.0, under BMI) (`renderBurn()`, called first in `renderProgress()` so it shows even if the chart library can't load). Maths in `Nutrition.realBurn()` (pure, tested):
- burn = average kcal eaten on qualifying days − weight-trend slope × 7,700 kcal/kg, over the **last 28 days** (today excluded).
- Qualifying day = ≥ 800 kcal logged (lower days are assumed not fully logged and skipped — owner chose automatic skipping over a "day complete" tick).
- Shown once there are **≥ 14 qualifying days and ≥ 3 weigh-ins spanning ≥ 14 days**; before that the card shows progress bars toward both.
- Weight trend = Theil–Sen line (median of pairwise slopes): on simulated data about as accurate as least squares with normal noise (typical error ~65 kcal) but a single 2 kg-off reading moves it ~60 kcal instead of ~280.
- Results outside 1,000–6,000 kcal are treated as unreliable ("numbers don't add up yet"), with no suggestion.
- Card figures (owner's request): **real burn / day, avg eaten / day, avg deficit (or surplus) / day** — deficit = rounded burn − rounded eaten so the three always add up — plus the period (logged days, dates, weight trend, weigh-ins) and a comparison with the formula maintenance estimate.
- **Never suggests eating more** (owner's rule, for any goal). `Nutrition.burnSuggestion()` = max(1,200, burn + goal delta) rounded to 10, offered only if ≥ 100 kcal below the current target (smaller gaps are within the estimate's wobble). Otherwise: "✓ … no change needed".
- Suggestion is one-tap: **Apply** sets the calories, rescales macros via `applyMacros()` (preset/keto/custom split kept) and turns **Calories from profile off** so the formula can't raise it back (toast says so). **Not now** stores `burnDismissed` and hides it for 7 days unless the suggestion falls another 100 kcal.

**Weight & BMI**
- **Starting weight** is entered once in Profile, then locked. It becomes the first reading, dated the day it was entered. A **"Correct"** link (with confirm dialog) unlocks it to fix a typo; saving rewrites that first reading only. Logging on the same day as the start updates the starting reading rather than duplicating.
- **Progress is the only place to log weight.** One reading per calendar day; re-logging the same day **overwrites** and says so ("Today's reading updated: 84.2 → 84.0 kg"; button reads "Update today"). Rationale: intra-day fluctuation makes the trend noisy; the UI nudges "same time each day, ideally first thing". The entry box starts empty with placeholder "Enter today's weight", shows a "kg" suffix once a number is typed, and the Log button is grey/disabled until the value is valid (20–400).
- Forecast panel heading is just "Forecast"; its note is two lines (Plan intake / Avg intake definitions), no "30 days" sentence (1.12.0).
- Under the weight chart, a **Recorded** table row: Start kg (with date) · Now kg (with BMI and date) · Kg since start (green when down, red when up). Replaced the earlier KPI pills in 1.10.4. Both this and the forecast table sit in their own tinted panel with a bold title ("Recorded" / "Forecast") so they read as two distinct sections.
- **Weight forecast** (toggle on the Weight card, on by default, persisted as `showForecast`): 30 days ahead from a **7-day smoothed** starting weight. Two projected lines — **Plan intake** (dashed indigo; eats the calorie target every day) and **Avg intake** (dotted amber; average logged kcal over the last 14 days, needs ≥3 logged days, today excluded) — plus a faint dotted **Target weight** line and a vertical "today" marker. Maths in `Nutrition.projectWeight`: 7,700 kcal/kg, maintenance re-derived daily from projected weight. A compact **table key** under the chart: rows Plan intake / Avg intake (Recorded has its own table above); columns Daily kcal · Target BMI (kg beneath) · Forecast date (estimated date + duration via `Nutrition.daysToTarget`, searched up to 2 years, else 'Not at this pace'). The 30-day end weights are stated in the note under the table.
- **BMI card** (own card, directly under Weight): BMI value + category; a settable **Target BMI** (default 24.9); a colour scale 12–40 (blue <18.5, green 18.5–24.9, yellow 25–29.9, red 30+) with the **matching weights for the user's height along the top** at 18.5 / 22 / 25 / 30 / 40 and the **BMI values along the bottom**; 22 is shown only as a marker (the old "middle of range" box was removed on request). Markers: **You** = solid dark circle, **Target** = hollow diamond; the bar has 12 px clearance so markers never overlap the label rows. A key lists both with their BMI and kg. Sentence: *"Lose x kg to reach target BMI of 24.9 (80.7 kg)."* / "You're x kg under…" / "right on…".
- **Progress screen order: Weight → BMI → Calories this week → Macros this week.**

**Add screen layout (1.16.0)**: action row (＋ Custom food · ＋ Recipe · ⇩ Import, compact 36 px buttons) sits **above** the filter chips; chip order is Results · Recents · **Recipes** · Favourites · My foods (Recipes third so it's reachable without scrolling the chips). **Foods**
- **CoFID foods display a friendly name** (`name`) with the official wording retained in `cofidName` — never show `cofidName` to the user (owner's choice: hide it completely).
- Three sources searched together: user's custom foods & recipes (instant), bundled CoFID UK foods (instant; ranked by `js/ranking.js` — see §2 — so everyday words surface the obvious food first), Open Food Facts products (debounced 700 ms / on Enter; the OFF search endpoint is rate-limited to ~10/min, so never search-as-you-type without the debounce). OFF barcode lookups retry 12↔13-digit variants (UPC-A vs EAN-13).
- Product images come from OFF (`image_front_small_url`). CoFID foods and recipes get an emoji chosen from the name.
- **Custom food form is minimal**: Name, Energy, Protein, Carbs, Fat, then Brand and Barcode (optional) at the bottom, plus the optional product photo. Sat fat / sugars / fibre / salt / serving size are no longer shown or asked for (existing values are preserved on edit).
- **Custom food from a label photo**: image is downscaled to 1600 px, greyscaled and contrast-stretched, run through Tesseract (`preserve_interword_spaces`), then `Nutrition.parseLabelText` picks the per-100 g column. It **pre-fills, the user confirms** — never auto-saves. Unknown barcodes offer "Create custom food" and remember the barcode so the next scan finds it locally.
- **Recipes**: ingredients via search/scan **or "From my diary"** — a picker with day chips for the last 7 days (today default, badge shows item counts), tick items, "Select all", selections persist across days; items arrive with the grams that were logged. Recipes can have a **photo** (1.17.0): thumbnail + "Add/Change photo" at the top of the recipe editor using the same Take photo / Choose from gallery chooser as custom foods, plus "Remove photo". Stored once as a photo reference in `recipe.image` (see §3; before 1.20.0 it was an embedded data URL) (shows in lists, the food sheet and diary entries via `recipeAsFood`). Not included in share links (data URLs are stripped to keep links short). Per-100 g values are computed from unrounded totals; servings and optional cooked weight set the portion size.

**Recipe building safety & speed (1.18.0)**:
- **Auto-saved draft** (`Store.state.recipeDraft`): the editor saves on every change (name, servings, cooked weight, gram edits, add/remove ingredient, photo) via `autosave()`, but only when `recipeIsDirty()` (new recipe with any content, or an existing one that differs from its saved copy). Saving or deleting clears it. Opening the editor fresh (＋ Recipe, Edit recipe) with a dirty draft shows "Unsaved recipe — Continue it / Discard it and …". The Recipes tab shows a dashed "Unsaved recipe … tap to continue" row at the top, with a square red **trash-can button** beside it (1.19.1) → "Delete unsaved recipe?" confirmation (Delete / Cancel); for an edited saved recipe it says the saved version stays as it is. The prompt's options read "Continue it" / "Delete it and start a new one" (or "Delete it and open …"). Owner's wording rule: use **Delete**, never Discard. Returning from the ingredient search / diary picker passes `{ resume: true }` so no prompt. Reason: tapping the dimmed backdrop or swiping back on iOS closed the sheet and lost the in-memory recipe. Owner chose auto-save only (not a "discard?" confirm on backdrop tap).
- **Back to results**: a food page opened from the ingredient search has "← Back to results" (`openFoodSheet({ onBack })`), which reopens the picker with the same query (`openIngredientPicker(..., { query })`), cached product results (`ipOffCache`) and no keyboard pop.
- **Remembered picks** (`Store.state.picks`, `Store.rememberPick/pickFor`, key = lowercase trimmed query with a trailing plural s dropped, max 300): when a food is added from a search — main Add search (via `fromQuery`) or the ingredient search — it's remembered for that search text and shown first under "Your pick last time" in both places (owner chose "everywhere"). Recipes are never pinned in the ingredient search.

**Speed work 1.21.0 (behaviour unchanged)**: search results identical to 1.20.0 (compared on 179 searches) but ~18× less work while typing; start-up no longer renames foods; the recipe draft is still kept in memory on every keystroke but written to storage only after a 1 s pause (or immediately when the app is hidden/closed — `visibilitychange`/`pagehide` flush); other changes still save within 50 ms (`Store.save(delay)`, an earlier deadline always wins); charts are created once and updated in place, skipped entirely if their data didn't change (`draw(id, cfg, extra)` signature); number/date formatters are built once (`fmt`, `fmtDateOpts`); one label-reading worker is reused and closed after 3 idle minutes; product search caches keep the last 20 queries. Not done (judged not worth the risk now): splitting the diary into one storage key per day (a year is ~0.4 MB since 1.20.0, so a full save is a few ms); throttling the scanner's frame rate (1.18.0 tuned it for speed).

**Data upgrade 1.20.0 (photos stored once) — how it protects data**: `Store.upgrade()` runs on every launch (no-op once `dataVersion` is 2). Steps: (1) untouched safety copy of the old localStorage document into IndexedDB `safety:before-1.20` (kept if a previous attempt already saved one; read back and compared); (2) the upgrade is done on a COPY: every embedded photo stored once (each write read back and compared); (3) the copy with photos put back must equal the original byte-for-byte; (4) the same change is applied in place to the live data (so anything logged meanwhile is kept) and written; (5) the written document is read back, recounted (days, entries, recipes, custom foods, weights, favourites, recents, photo uses must not drop) and every reference must resolve. Any failure → photo change undone on the live data, `dataVersion` stays 1, retried next launch. The app draws Today immediately and shows a one-time "Data upgraded ✓" sheet with the counts. Tested on the owner's real backup (67 entries, 10 days, 7 recipes, 5 custom foods, 8 weights, 6 photos ×26 → 327 KB became 55 KB + 61 KB photos, round-trips identical) and with injected failures (photo write fails, photo reads back corrupt, storage full at switch-over, IndexedDB unavailable, logging during the upgrade).

**Backup & restore (1.20.0)**: backup format 2 = `{ app, format: 2, exportedAt, data (with photo refs), photos: { id: dataURL } }` — each photo once (the owner's backup shrank 352 KB → 142 KB). Restore (`importJSON`, async) accepts format 2 and the old format (photos embedded) and converts; it first saves `safety:before-restore` (what was on the phone). Me → Backup shows whether storage is protected, plus "Download the copy saved before the 1.20 upgrade / before your last restore" (rebuilt as a restorable format-2 file). Older app versions can restore a format-2 backup but would lose the photos.

**Recipe view (1.19.0)**: the recipe's food page shows **View recipe** (not "Edit recipe"). `openRecipeView(r, onBack)` is read-only: photo, servings and weights, per-serving kcal/macros, every ingredient with grams and kcal, whole-recipe totals, then **← Back** (returns to the food page with the same options) and **Edit recipe** (opens the editor, so the draft prompt still applies). Purpose: let users recreate a meal from the ingredient list without risk of changing it. The button only shows if the recipe still exists (a diary entry can outlive a deleted recipe).

**Panel history (1.19.0 fix)**: panels push a history entry so the phone's back gesture closes them. `closeSheet()` (non-silent) calls `history.back()`, whose `popstate` arrives asynchronously; if a new panel was opened in between (Save recipe → saved recipe panel; Import → imported item panel) that late popstate used to close it. `selfBacks` counts app-initiated backs; their popstate is ignored and a fresh history entry is pushed if a panel is open. Tests model real browsers by making `history.back()` async.

**Forecast switch (1.18.0)**: the "Forecast" toggle on the Weight card only shows/hides the projected lines (and target line / today marker) on the chart. The Forecast summary table is always shown.

**Sharing (1.13.0)**: ⇪ button on the food sheet for recipes and custom foods → `navigator.share` with a summary + link + iPhone instructions (fallback: copy box). `checkIncomingShare()` reads `#share=` on launch/hashchange and opens the import sheet; **Add → ⇩ Import** lets the user paste a link/code. Import sheet shows a preview, a **Save as** name field pre-filled with the shared name — red border + hint while the name is empty or already used, button disabled — and, when not running as an installed app on iOS, a "Copy code" button plus a note explaining to import inside the home-screen app (iOS opens links in Safari, whose storage is separate). No duplicates/overwrites are ever created.

**Out of scope (deliberately)**: cloud sync, multiple profiles, micronutrient targets (fibre/sugar/salt are shown when known but not tracked), fully automatic label reading without confirmation, Breakfast/Lunch/Dinner grouping. A note under the "Calories from profile" toggle ("Off: targets stay fixed as weight changes") was offered and not yet requested.

## 5. Open Food Facts & CoFID specifics

- OFF: `world.openfoodfacts.org/api/v2/product/{code}.json?fields=…` for barcodes; `uk.openfoodfacts.org/cgi/search.pl?…&json=1` for name search (UK subdomain ranks UK products first). CORS is open; no API key. Licence ODbL — attribution is in the About card and README.
- CoFID (McCance & Widdowson 2021, Public Health England, Open Government Licence v3): the workbook's **"1.3 Proximates"** sheet has 3 header rows (names / abbreviations `PROT FAT CHO KCALS KJ TOTSUG AOACFIB SATFOD` / units) then data. `Tr` = trace → 0, `N` = unknown → null. `tools/build_cofid.py` and `Nutrition.parseCofidRows` both locate columns by abbreviation first, header name second. Food group letter → friendly name map (`COFID_GROUPS`) lives in `app.js`.
- The build environment used so far **cannot download binary files from the internet**; the spreadsheet was obtained by the owner saving it to OneDrive. Keep `data/cofid.json` in the repo so no device ever needs to import it.

## 6. Service worker & updates

- `sw.js` precaches the app files with `cache: 'reload'` (fresh from the server, never the browser's 10-minute HTTP cache) and serves same-origin requests **cache-first (instant)**. Cache-first replaced network-first in 1.10.0 because iOS let offline requests hang 30–60 s, leaving a blank screen. **Since 1.21.0 there is no background refresh**: before, each launch re-fetched every file into the current cache, so a phone that opened the app while an upload was half-way through could keep new `app.js` with old `store.js`. Now files change only when `VERSION` changes, all together. New releases still appear promptly because the app calls `registration.update()` on launch and reloads on `controllerchange`. OFF API calls are never cached by the SW (the app caches lookups itself).
- `app.js` registers with `{ updateViaCache: 'none' }`, calls `registration.update()` on launch and whenever the app returns to the foreground (throttled to 5 min), and **reloads automatically on `controllerchange`** after showing "Updating to the latest version…". **Me → Check now** forces a check and reports the result. The version shows at the bottom of Me.
- Changing `VERSION` in `sw.js` is what triggers an update on devices. Forgetting it means the phone keeps the old files.
- **Product pictures (1.20.0)**: Open Food Facts images go through `productImage()` into their own cache `fooddiary-product-images` (NOT tied to the app version, so kept across updates), capped at 150 (oldest removed). They are fetched with `mode:'cors'` and stored only if the response is not opaque; if CORS fails the picture is shown but not stored. Reason: opaque responses count ~7 MB each against Chrome's quota, and the old code cached them without limit — on Android that could lead Chrome to clear the app's storage (diary included). The app also calls `navigator.storage.persist()` on launch.
- **Long-lived caches (1.21.0)** — kept across app updates, so an update only downloads the small app files:
  - `fooddiary-data-N` (`DATA`): `data/cofid.json`. Installed only if missing. **Bump `DATA` when the food list changes** (e.g. after `tools/bake_names.js`), or phones keep the old list.
  - `fooddiary-libraries-N` (`LIBS`): CDN libraries (Chart.js, barcode-detector/ZXing wasm, Tesseract + language data, SheetJS). All URLs are pinned to exact versions. Fetched with CORS first (stored at real size), falling back to a normal request (opaque, still stored — only a handful of files). **Bump `LIBS` if you change a library version.**
  - `fooddiary-product-images` (below). Everything else is deleted on activate.

1. Make the change. Keep `nutrition.js` DOM-free so it stays unit-testable.
2. Bump **all three**: `APP_VERSION` in `js/app.js`, `VERSION` in `sw.js`, "Current version" on line 3 of `README.md`. Patch for tweaks (1.9.1), minor for features (1.10.0).
2a. Check the change against the two standing rules in §10 (efficient on iPhone + Android; ask first if anything could break or lose data).
2b. **Update this HANDOVER.md in the same release** — owner's standing instruction (5 Oct 2026). Record any new product decision in §4, new files in §2, data-model changes in §3, and append a line to the changelog in §12. A zip whose handover notes lag the code is a defective release.
2c. If `js/names.js` or the CoFID data changed: `node tools/bake_names.js` and bump `DATA` in `sw.js`. If a CDN library version changed: bump `LIBS`.

4. Run the smoke tests (§8).
5. Zip the folder **contents** as `FoodDiary-vX.Y.Z.zip`. **Keep the three most recent release zips** in the output folder and delete anything older (owner's rule since 1.13.0; before that only the latest was kept). No unpacked folder alongside.
6. Tell the owner which files changed; they upload to the GitHub repo via *Add file → Upload files* (folder contents, not the folder). Pages publishes in ~1 min; phones self-update on next open.

## 8b. UI rule learned the hard way

Never re-render (`innerHTML =`) a container that holds the input the user is typing in, from that input's own `input` event. It replaces the focused element, so mobile browsers drop focus and close the keyboard after one keystroke. Split rendering into a structural redraw (on add/remove) and a values-only refresh (on typing). The recipe editor uses `drawList()` / `drawTotals()` for this (fixed 1.16.4).

## 9. Design language

Modern, clean, "not an engineering demo": 18 px radius cards with soft shadows, system font stack, generous spacing, a hero calorie **ring** (SVG, `stroke-dashoffset`) with macro **progress bars** that read "x g left" / "x g over" (bars turn red when over), Chart.js charts with rounded bars and a dashed target line, a bottom **sheet** for every detail/edit flow, pill chips, a frosted tab bar. Light/dark follows the OS. Icons were generated with Python Pillow (green gradient, white ring, fork & knife) at 192/512/maskable 512/180 px.
